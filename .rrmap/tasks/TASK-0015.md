AI生成の文章は「説明の段落→箇条書き→段落」の繰り返しになる。`p + ul`を詰めて`ul + p`を空けると
塊の境目が見える。TASK-0013のリスト内の余白と一緒に調整しないと間延びするので、同時に見る。

## 実装メモ (2026-09-24)

`.markdown-body p:has(+ ul), p:has(+ ol)`に`margin-bottom: 0.25em`(4px)、
`.markdown-body ul + p, ol + p`に`margin-top: 1.5em`(24px)を入れた。

できあがった余白のはしごは、狭いほうから
段落→箇条書き 4px / 項目↔項目 8px(TASK-0013) / 段落↔段落 16px / 箇条書き→段落 24px / 見出しの上 36px。
beforeはこのうち3つが同じ16pxで、塊の境目に順番が付いていなかった。

### 値の決め方

上(段落→箇条書き)は0 / 0.25 / 0.5emを実測して比べた。0だと段落の次の行がそのまま項目になったように
見えて一覧の始まりが分からない。0.5emは項目どうしの8pxと同じ幅になり、1項目目だけが段落側にも
一覧側にも寄らずに浮く。いちばん狭いところが段落と箇条書きのあいだになる0.25emを取った。

下(箇条書き→段落)は`ul`の`margin-bottom: 1em`と相殺されるため、1emより広い値でないと動かない。
`ul + p { margin-top: 0.5em }`と書いても16pxのまま。1.25 / 1.5 / 2emで比べて、1.25emは段落どうしとの
差が4pxしかなく見分けが付かない、2emは見出しの上の36pxに近づいて階層が平らになる。1.5emで止めた。

### 確認したこと

詰めた分(−152px)と空けた分(+128px)が釣り合うので、ページ全体はむしろ24px縮む(4850→4826px)。
余白の総量は増やさずに配り方だけを変えたことになる。コードブロック・表・見出しまわりは1pxも動かない。

副産物として、ルーズリストの中で0pxだった「ネストした箇条書き→そのあとの段落」が24pxになった。
TASK-0013で`li > ul`の`margin-bottom`を0にした影響で、箇条書きと次の段落がくっついていた場所。
逆に項目の中の「段落→ネストした箇条書き」は`li > ul { margin-top: 0.5em }`が相殺で勝つため8pxで止まる。
ネストは階層の話なので、項目どうしと同じ8pxのままでよいと判断した。

`p:has(+ ul)`と`ul + p`は隣り合わせが条件なので、本文に要素を差し込むコメントのスロットを確かめた。
既定(句点ごとの改行が有効)ではカーソルのtargetが`.mdecho-sentence`なので、スロットは`p`の内側に入る。
`p`と`ul`は隣り合ったままで、コメントを開いても4pxのまま変わらない。

### 残っている課題

`--no-split-sentences`のときだけ、targetが`p`自身になってスロットが`p`と`ul`のあいだに入り、
`p:has(+ ul)`が外れて16pxに戻る(実測済み)。`p:has(+ .mdecho-comment-slot + ul)`まで書けば塞げるが、
同じ行に複数のコメントが付くとスロットが連なるので、その数だけセレクタを並べることになる。
カード自体が区切りとして働いている場所なので入れていない。

箇条書きどうし(`ul + ol`)は16pxのまま。塊と塊が隣り合う場所なので段落どうしより広くてもよさそうだが、
前後の4pxと24pxに挟まれて十分に見分けられていたため、広げる根拠が見つからなかった。

TASK-0013から持ち越しのルーズリストの段落間は今回も手つかず。`ul + p`が効いて箇条書きの下だけは
24pxになったが、段落が続くところは16pxのまま。コメント欄(`.mdecho-comment-view-body`)は
TASK-0010・TASK-0013と同じ理由で範囲から外した。

TASK-0016で行間を設定項目にする場合、4pxも24pxも文字サイズ基準なので行間には追従しない。
行間を広げると段落どうしの16pxが行間に埋もれていくため、そのときにはしご全体を見直す余地がある。
